# 基金净值自动获取与手工兜底设计

日期：2026-09-29  
状态：已确认，待实施

## 1. 目标

基金净值的日常更新改为自动获取优先。用户只在所有自动正式净值来源均失败、首次录入或需要纠错时手工输入。系统继续区分正式净值与盘中估算，不使用估算值确认总资产。

## 2. 数据源优先级

对每只已登记的中国公募基金，交易日的每日检查按以下顺序处理：

1. 使用现有 `EastMoneyFundNavProvider` 获取最新正式净值。
2. 主来源失败时，使用 `EfinanceAdapter.fetch()` 获取正式净值。
3. 两个来源都失败时保留最后一条有效正式净值，记录失败审计，并把该基金标记为需要手工补录；不得把旧净值或零值伪装成当天净值。

历史净值继续由 `EfinanceAdapter.fetch_history()` 补齐。只有当前正式净值刷新失败时才触发正式净值回退，避免无意义的重复请求。

## 3. 盘中估算边界

`EfinanceEstimateAdapter` 可用于独立获取盘中估算，但盘中估算必须：

- 以 `intraday_estimate` 类型单独保存和展示；
- 显示来源、抓取时间和“估算”标识；
- 不覆盖同日正式净值；
- 不参与 `PortfolioSnapshot.total_value_cents` 的完整确认；
- 不单独触发确定性的买入、卖出或减仓建议。

第一阶段只接入自动正式净值回退。盘中估算保留现有适配器和数据模型能力，不增加额外提醒，以免用户把估算误认为结算净值。

## 4. 自动重算与确认规则

任一自动来源成功写入新的正式净值后，当天已有的组合快照应立即重新估值。重算沿用快照中原有的现金和持仓确认时间，不因行情获取成功而自动确认现金或持仓。

总资产只有在以下条件同时满足时才显示为完整值：

- 所有正数持仓都有符合日期要求的正式净值；
- 持仓数据已确认且未过期；
- 现金数据已确认且未过期；
- 资产和账户币种受支持。

任一条件不满足时继续显示“未确认”，但可展示有来源依据的已知部分。

## 5. 手工录入与提示

手工净值页面继续保留，定位为异常兜底和纠错入口。每日任务只有在两个自动正式净值来源都失败时，才生成“需要手工补录”的提示。提示包含基金名称、代码、最后有效净值日期和自动来源失败状态，不包含虚构价格。

用户保存手工正式净值后，系统沿用现有逻辑重算当天组合快照。自动来源之后恢复时，不删除手工记录。同一日期存在多个有效正式来源时，按“手工纠错、EastMoney 主来源、efinance 回退来源”的顺序选择；同一来源存在重复更新时选择最新抓取记录。快照详情必须保存最终采用的来源和抓取时间，保证选择过程可审计。

## 6. 错误处理与审计

- 每个来源的失败独立记录，包含来源、时间、有限长度的错误摘要和尝试次数。
- `efinance` 缺失、超时或返回无效数据时视为回退失败，不影响每日任务处理其他基金。
- 单只基金失败不得中断其他基金刷新。
- 自动流程不得修改持仓份额、成本、现金余额或发起交易。
- 通知中不得声称预测下一交易日涨跌或保证收益。

## 7. 测试与验收

自动化测试至少覆盖：

1. 主来源成功时不调用回退来源。
2. 主来源失败、`efinance` 成功时写入正式净值。
3. 两个来源都失败时保留最后有效净值并记录手工补录提示。
4. 一只基金失败时其他基金仍能刷新。
5. 正式净值写入后自动重算当天已有快照。
6. 盘中估算不能覆盖正式净值或确认总资产。
7. 缺少现金或持仓确认时，自动净值成功后总资产仍为“未确认”。

发布前执行完整 pytest、Ruff、mypy、迁移检查和线上健康检查。部署后验证 GitHub `main`、服务器当前 release、服务状态和 `/health` 一致。

## 8. 不在本次范围

- 自动买入、卖出或调用基金交易接口；
- 使用大模型预测净值涨跌；
- 将 `funds` 或 `real-time-fund` 作为常驻 Node 服务部署；
- 以盘中估算替代正式净值完成资产确认。
