# 官方基金净值同步设计

日期：2026-09-30  
状态：已完成对话设计确认，等待书面规格审核

## 1. 背景与结论

生产环境验证表明，东方财富在 2026-09-30 14:00 返回的最新官方净值日期为 2026-09-29，这符合基金净值通常在收盘后公布的规律。现有天天基金 JSONP 盘中估值地址已经返回“页面未找到”，东方财富实时基金接口中的估算净值、估算涨跌幅和估算时间字段也均为空。因此平台不再展示或调度盘中估值，只保留可核验的官方净值。

本设计取代以下既有设计中的盘中估值部分：

- `2026-09-29-automatic-fund-nav-fallback-design.md` 第 3 节；
- `2026-09-29-fund-data-center-design.md` 中所有盘中估值、盘中估算盈亏和高频估值刷新要求。

历史风险指标、手工净值纠错、总资产只使用官方净值等既有要求继续有效。

## 2. 目标

- 自动保存上游已经公开的最新官方净值，不把尚未公布的当日净值视为抓取失败。
- 在基金公司收盘后公布净值时自动补齐数据，而不是只在 14:00 查询一次。
- 页面只展示官方净值及其真实日期、来源和获取时间。
- 保留手工净值作为异常补录和纠错入口。
- 停止调用失效的盘中估值接口，避免重复失败、无效网络请求和审计日志膨胀。

## 3. 数据来源与可信边界

每只当前持有的中国公募基金按以下顺序获取官方净值：

1. 使用现有 `EastMoneyFundNavProvider` 获取最新官方净值；
2. 主来源失败时，使用 `EfinanceAdapter` 获取官方净值；
3. 两个来源都失败时保留最后一条有效官方净值并记录有限长度的失败摘要。

所有自动记录使用 `quote_type=official_nav`。平台不得根据涨跌幅、重仓股、指数走势或模型自行推算净值，也不得把历史净值复制为当日净值。上游最新日期早于当前日期时，只要请求成功且数据有效，就显示“上游最新官方净值为 YYYY-MM-DD”，不显示为系统故障。

`efinance` 运行所需的包内数据目录在部署时预先创建，使其能在 systemd 只读发布目录策略下正常导入；不放宽整个发布目录的写权限。

## 4. 独立同步任务

新增独立的官方净值同步命令和 systemd 定时任务，不复用下午 2 点的建议提醒任务。同步范围只包含持仓数量大于零、市场为 `CN`、资产类型为 `fund` 的去重基金代码。

调度时间采用北京时间：

- 周一至周五 `18:00`、`20:00`、`22:00`；
- 周二至周六 `08:00` 补查前一交易日可能延迟公布的净值。

项目已配置的中国法定节假日应跳过对应交易日的晚间刷新。早晨补查可以运行但不得发送通知；若上游仍返回同一条最新官方净值，则记为成功且不生成重复价格记录。

旧 `finance-market.timer` 和 `finance-market.service` 退役并在部署时停止、禁用和移除，避免继续请求失效的盘中估值接口。新任务使用清晰的 `finance-nav` 命名，日志与 `finance-daily` 建议提醒相互独立。

## 5. 页面与交互

基金数据中心只显示以下行情信息：

- 最新官方净值；
- 官方净值日期；
- 数据来源；
- 最近获取时间。

删除“盘中估值”“估算涨跌”“估算盈亏”等字段、样式和文案。原“刷新行情”操作改为“获取最新官方净值”，仍使用 POST、CSRF 校验和单基金冷却机制。手动刷新只调用官方净值提供器链。

当上游尚未公布当日净值时，页面继续展示最近官方净值，并明确写出其净值日期。没有任何官方净值时显示“暂无官方净值”，不得显示 0。

风险分析、持仓金额、收益率、资产总览和组合快照继续只读取官方净值。历史数据库中已经存在的 `intraday_estimate` 记录可以保留用于审计，但不再展示、刷新或参与任何计算。

## 6. 下午 2 点提醒

下午 2 点提醒时间和交易日规则保持不变。提醒使用当时已公开的最近官方净值，并明确标注净值日期。由于当日官方净值尚未公布，提醒不得暗示数据代表当天收盘结果，也不得因为缺少当天官方净值而要求用户手工补录。

净值同步任务不发送买卖提醒。提醒任务与官方净值同步任务分别失败、分别记录，不相互阻塞。

## 7. 错误处理与审计

- 单只基金失败不得中断其他基金同步。
- 主来源失败、备用来源成功时，任务整体视为该基金成功。
- 所有来源失败时保留最后有效记录，不写入空值、零值或猜测值。
- 同一基金、来源、官方净值日期和报价类型重复获取时更新获取信息或保持幂等，不产生无界重复记录。
- 任务汇总输出尝试、成功、未变化和失败数量。
- 失效的盘中估值错误不再重复写入审计表。
- 自动流程不得修改持仓份额、成本、现金余额或交易记录。

## 8. 部署与兼容性

- 不需要修改现有生产理财数据，也不需要新增数据库迁移。
- 部署前创建并校验在线备份。
- 部署脚本安装新 `finance-nav.service` 和 `finance-nav.timer`。
- 部署脚本显式退役旧 `finance-market` 单元，执行 `daemon-reload` 后确认旧定时器不存在。
- Nginx、Tailscale、SSH、通知邮箱和现有提醒配置保持不变。
- 新 release 切换后验证官方净值任务可以在 systemd 安全策略下导入 `efinance`。

## 9. 测试与验收

自动化测试至少覆盖：

1. 官方主来源成功时保存官方净值且不调用备用来源。
2. 主来源失败时使用 `efinance` 官方净值回退。
3. 上游最新日期早于当前日期时视为有效结果并正确展示日期。
4. 同一官方净值重复获取时保持幂等。
5. 一只基金失败时其他基金仍可同步。
6. 晚间刷新、次日早晨补查、周末和法定节假日的调度边界。
7. 页面和通知中不再出现盘中估值、估算涨跌或估算盈亏。
8. 手动刷新只获取官方净值并保留 CSRF 与冷却限制。
9. 总资产、组合快照和风险指标只使用官方净值。
10. 部署产物包含新单元并显式退役旧 `finance-market` 单元。
11. `efinance` 在 `ProtectSystem=strict` 的服务环境下能够导入。

发布前运行 Ruff、完整 pytest 和部署产物测试。部署后验证 GitHub 默认分支、服务器 release、数据库完整性、服务状态、定时器时间表、网站登录页和基金数据中心。

## 10. 完成标准

- 网站只展示可靠的官方基金净值。
- 生产环境不再运行或记录盘中估值刷新失败。
- 收盘后公布的新官方净值能在当晚自动入库，延迟公布时由次日早晨补查。
- 用户无需为正常的净值公布延迟手工输入数据。
- 页面始终显示净值实际日期和来源，不把“最新可用”误写为“今日净值”。
- 现有持仓、成本、现金、历史净值和通知配置保持不变。
